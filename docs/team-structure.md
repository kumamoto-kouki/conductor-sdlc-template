# チームの読み方

このチームは誰で構成され、どういう約束で動くのかを、前提知識なしで読めるようにまとめる。

- **体制図**（誰が誰に報告するか）の正本は [`.kiro/steering/orchestration.md`](../.kiro/steering/orchestration.md)
- **配役表**（いま誰が座っているか）と**フェーズ別の投入計画**の正本は [`.kiro/steering/role-catalog.md`](../.kiro/steering/role-catalog.md)
- **いま誰が参画しているか**は [`../STATUS.md`](../STATUS.md)（`npm run status` が配役表から生成する）

**このページに正本は無い。**図や表を二重に持つと必ず片方が古くなるため、図は複製せず、正本の内容を前提知識なしで読めるように言い換えたものだけを置く。食い違いを見つけたら、正しいのは常に正本の側である。

## 💬 チームの約束 — 心理的安全性

このチームは心理的安全性を常に担保する。失敗・不明点・反対意見を安心して出せ、レビューは**人格ではなく成果物**に向ける。「分からない」「やり直したい」と言える率直さと、互いへの敬意を両立する。

🛡️ EngRev の指摘は 👨🏼‍💻 実装BE を責めるためではなく、品質を一緒に上げるためのものである。

## 誰が人間で、誰が AI か

- **🧑🏻‍💼 あなた（PO）は実在の人間**。大方針・承認・公開判断を担う。
- **担当名（👨🏼‍💼 統括・👩🏼‍💼 運用・🧑🏼‍💼 Engリーダー・🧑🏼‍🎨 Designリーダー・👩🏼‍🎨 デザイン実装・🕵🏼‍♀️ デザインRev・👨🏼‍💻 実装BE・👩🏼‍💻 実装FE・🛡️ EngRev・👨🏼‍🔬 QA）は AI エージェントの役割ペルソナ**であり、実在の個人ではない。役を固定することで責任の所在を明確にしている。
- **🧑🏼‍🏫 PO技術検証**は、実在の人間が座るときは PO の側に立ち、PO が単独では妥当性を確かめられない技術的回答を独立に確認する常設の席。成果物は作らず、受理判定も行わない（合否は 🛡️ EngRev）。AI で代替するときは、別の実体を立てることと、そのことを PO へ開示することが必須。**どちら側の席になるかは、人間か AI かでは決まらない**——その席の人（または AI）を PO 自身が選び、PO 自身が外せるなら PO の側、統括が連れてきて統括が指示するなら受注側の自己点検になる。テンプレートの既定は空席。
- **代弁ペルソナ（🙋 エンドユーザー代弁・🏭 現場代弁・🤝 ステークホルダー代弁）**は、意見ではなく**検証すべき仮説**を示す役（プロトペルソナ）であり、実在の人間の代替ではない。記入は断定でなく「未検証・根拠」つきの仮説形式で行う。実在の利用者・現場担当・ステークホルダーに直接当たれる場面、または 🧑‍🚀 FDE が投入されている場面ではそちらを優先し、代弁は両方とも無い場合のフォールバックである。
- **🧑‍🚀 FDE（フォワードデプロイド）**は現場・ステークホルダーへ直接常駐する実施者（Maker）で、権限は実装範囲内の自律調整に限定される。spec・スコープの変更は Discovery → PO 承認のフローを必ず通す。

各役の charter と境界の正本は [`.kiro/steering/role-catalog.md`](../.kiro/steering/role-catalog.md) にある。

## この体制が守っていること

| 観点                       | 内容                                                                                                                           |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 統括は実装しない           | 采配に専念し、采配自体も各レーン・リーダー（Engリーダー・Designリーダー）へ委譲する。                                          |
| 2つのレーン                | エンジニアリング（実装）とデザイン。どちらも同じ三役（コンダクター・実施者・レビュアー）で構成する。                           |
| 実施者は複数が並行         | 機能やコンポーネントごとに別々の作業者が同時に動く。コンダクターと受理（レビュー）が集約点になる。                             |
| **作る役とチェック役は必ず別** | 自分で作って自分で合格を出さない（甘い判定を防ぐ）。受理は報告ではなく**証拠**で行う。                                        |
| 運用は受理に介入しない     | 👩🏼‍💼 運用は運用状況の管理と相談窓口を担い、受理判断には関わらない。統括の自己評価バイアスを避けるための独立性である。            |
| デザインの証拠             | 見た目の好みではなく、コントラスト比（読みやすさ）・状態網羅・AI 開示の遵守・実装可能性で判定する。                            |
| デザインの作り方           | claude.ai/design で生成 → レビュー → `/design-sync` で1部品ずつコードへ取り込み → 公開は人間。                                 |

「作る役 ≠ チェック役」は規律 C として [`.kiro/steering/orchestration.md`](../.kiro/steering/orchestration.md) に正本がある。
