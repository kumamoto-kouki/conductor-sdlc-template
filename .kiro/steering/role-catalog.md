# role-catalog.md — 役割カタログ＋投入計画

運用マネージャー（👩🏼‍💼 運用）が管理する**役割の事前カタログ**。狙いは「必要な人を必要なタイミングで、役割を事前に把握して投入する」こと。役割を都度リアクティブに増やす運営の弱さ（仕組みの弱さ・blameless）への是正。正本の体制は `orchestration.md`、参照する外部仕組みは [[agent-skills-and-role-catalog]]（`github.com/addyosmani/agent-skills`）。

## 原則（投入のしかた）

- **カタログから計画投入する**（事前把握 ≠ 即時大量投入）。必要になってから慌てて新設しない。
- **運用（運用マネージャー）が「いつ誰を」を計画・上申** → 統括が委譲 → **PO（あなた）が承認**。
- 過剰配置を避ける：軽微はコンダクター直、専門観点は該当フェーズでのみ投入。

### QAの charter と境界（スコープ限定投入の例）

- **スコープ**: 回帰が多い時期／複雑機能のスプリント限定で投入（M＝節目専用・タスクは別系列で識別）。回収後に常設要否を運用が再判断し統括経由で上申。
- **担当**: テスト戦略・カバレッジ設計・回帰/エッジケースのテスト追加（DOM/E2E 拡充）。作り込み側＝Maker 寄り。
- **境界（EngRevとの分離）**: QAは**テストを足す／品質を作り込む**が**受理権限は持たない**。合否（証拠での受理判定）は 🛡️ EngRev（独立 Checker）。QA≠EngRev≠実装者の三者独立で自己評価バイアスを避ける。
- **きっかけ（型）**: 回帰が実観測されたら、兼務で凌がず専任を計画投入する（後追いで凌ぐ運営の弱さの是正）。

## 規模別プリセット（S/M/L）

配役は毎回ゼロから組み立てず、**プロジェクトの規模でプリセットを選んでから**必要な役だけ確定する
（`README.md` 起動チェックリストの前提）。プリセットは**投入する役の数**を変えるものであり、
**規律・原則そのものは変えない**——特に **Maker ≠ Checker（規律 C＝自己レビュー禁止）は規模に
関わらず不変**。S でも「実装した本人がそのまま受理する」ことは禁止で、独立レビューは必ず別実体が行う。

| プリセット            | 目安                                       | キャスト                                                                                                              | WIP 上限                                      |
| --------------------- | ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| **S（小規模・実験）** | 単一 spec・〜数十ファイル・並行なし        | 統括が**レーンリーダーを兼務**（采配の委譲先を省略）。実装 1 名＋独立レビュー 1 名の最小構成                          | 1〜2                                          |
| **M（標準）**         | 複数 spec・数百ファイル・worktree 並行あり | 現行の標準キャスト（統括／運用／Eng リーダー・Design リーダー／実装 BE・実装 FE・デザイン実装／EngRev・デザイン Rev） | 3（現行）                                     |
| **L（大規模）**       | 多 spec 並行・数千ファイル・複数 wave      | 標準＋**QA 常設**＋**設計（アーキテクト）を着手前に常設**＋セキュリティ／パフォ監査を節目ごと定期投入＋ライター       | 3（現行、必要ならレーン単位で運用が別途上申） |

### 判断の目安・兼務境界

| プリセット | 判断の目安（いつ選ぶか）                                                       | 兼務してよい役                                              | してはいけない分離                                                                         |
| ---------- | ------------------------------------------------------------------------------ | ----------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| S          | 実験・PoC・1人日〜数日で終わる小機能。並行開発が要らない                       | 統括＝レーンリーダー兼務（采配と受理統括の兼務は可）        | **実装者＝独立レビュー**（Maker≠Checker は不変）。実装者が自分の成果物を受理してはならない |
| M          | 複数機能を worktree 並行で進める・スプリントが継続する通常運用                 | 兼務なし（役職ごとに別実体）が既定                          | 統括＝実装（規律 A）。レーンリーダー＝Maker（采配は実装に着手しない）                      |
| L          | 複数 spec が同時に走る・ファイル数が多く影響範囲調査が頻発する・監査観点が要る | 常設役同士の兼務は避ける（QA≠EngRev は M と同じ境界を維持） | QA＝EngRev（QA はテストを足すのみ・受理権限は EngRev 独占）。監査役の兼務による見落とし    |

**プリセットの移行（S→M→L）は起動時に先読みで決め打ちしない**。プロジェクトが成長したら、
wave 境界・マイルストーン境界などの**節目で見直す**（着手直後の頻繁な体制変更はドリフトの温床になる
ため避ける）。

| 🧑‍🚀 FDE（フォワードデプロイド） | 実在の現場・ステークホルダーに直接常駐し、要求理解から実装まで一気通貫で担う（Eng/Design 両レーン対応。出典: [Forward Deployed Engineer](https://zenn.dev/hellorusk/articles/f75f6d41b0a30c)） | 単一顧客・現場への深い密着が要る個別カスタマイズ案件・PoCから本番移行までの伴走 | 候補 |

**代弁ペルソナ（🙋/🏭/🤝）の使命**：需要側（利用者・現場・ステークホルダー）の関心事が、供給側（作り手にとって都合のいい判断）の都合だけで静かに押し流されるのを防ぐ、Discovery 時の強制チェックポイント。3 観点を別見出しで書かせるのは、まとめて「関係者」と1つに書くとその時々で都合のいい1視点に収束してしまうため（現場は「手数を減らしたい」、ステークホルダーは「コストを抑えたい」等、本来ぶつかり得る利害を残す）。

**代弁ペルソナの運用形態（重要）**：代弁ペルソナは**意見を述べる役ではなく、検証すべき仮説を明示する役**（UXデザインの「プロトペルソナ」と同じ位置づけ）。「〇〇は××と思うはずだ」という断定でなく、「〇〇は××と想定している（未検証・根拠: なし／伝聞／推測）」の形で書く。実在の人間の代替ではなく、**実在アクセスまたはFDEが利用可能ならそちらを既定にし、代弁ペルソナは両方とも無い場合のフォールバックとして使う**。実在者・FDEの一次情報と代弁の仮説が食い違ったら実在者・FDEを優先し、食い違い自体を開示する。

### FDE の charter と権限境界（現場直接アクセスの例）

- **役割**：エンジニアリングまたはデザインの実施者（実装BE/実装FE/デザイン実装のいずれか）が、現場・ステークホルダーへ直接常駐してニーズを深く理解し、既存プラットフォームを現場に合わせて実装する。役割としては Maker（実施者）の一種であり、別系統の役職ではない。
- **権限範囲（重要・誤用防止）**：**実装範囲内の自律調整のみ**を認める（UI文言・エラーメッセージ・細かい挙動など、既存 spec の受け入れ条件を変えない範囲の現場適応）。**spec・スコープ自体の変更は既存の Discovery→PO承認フローを必ず通す**（`kiro-discovery`／3フェーズ承認）。FDEが現場で得た知見は `TEMPLATE-FEEDBACK:` マーカーと同型の**提案**として還流し、統括経由でPOが判断する。現場密着の速度を理由に承認ゲートを迂回しない。
- **Maker≠Checker は不変**：FDEも実装者であり、自分の成果物を自分で受理しない。独立レビュー（EngRev／デザインRev）は他の Maker と同様に必須（規律C）。
- **FDEの現場情報は優先度の高い根拠であって、無条件の正解ではない**（代弁ペルソナより信頼できるが、単一の接点・限られたサンプルからの解釈である可能性は常に残る）。誰から・何件・どういう文脈で得たかを開示し、既存のプロダクト前提や他のステークホルダーの声と矛盾する場合はその矛盾ごとPOへ上申する。「FDEが言った」こと自体を受理の根拠にしない。
- **投入の目安**：単一顧客への深いカスタマイズ・PoCから本番移行までの伴走など、通常の worktree 並行実装では現場密着の速度に追いつけない案件でのみ投入判断する。通常のスプリント運用（M/L プリセットの標準実装フロー）に置き換わるものではない。

## 次プロジェクトへ（seed）

この配役表＋候補ロスターを seed として引き継ぎ、立ち上げ時に agent-skills のロスター（code-reviewer / test-engineer / security-auditor / web-performance-auditor）と**統合した配役表**を最初に確定する。背骨（Kiro か agent-skills）はそのとき1つ選ぶ（二重ツール回避）。
