2026-06-29 このテンプレートの経緯・決定・継続手順

このディレクトリ（conductor-sdlc-template）で作業を継続するための記録。何を・なぜ作り、どんな決定でこの形になったか、次に何ができるか。まずこの1枚 → README.md（始め方）→ .kiro/steering/（正本）を読む。

何か（一言）

実プロジェクト（Tauri デスクトップアプリ）の開発で確立した**「AI エージェント主体の進め方」——コンダクター・オーケストレーション＋Kiro Spec-Driven Development＋可視化ダッシュボード——を、次プロジェクトの起点として切り出したテンプレート**。アプリのコードは含まず、進め方の骨格だけ。

経緯（どうして生まれたか）

元プロジェクトを保留（.claude/reports/ の handoff・元リポジトリの GitHub issue に記録）する際、そこで培ったノウハウを次に活かすため PO 指示でテンプレート化した。名前は conductor-sdlc-template（署名的手法を一目で表す記述的な名前）を PO が選択。

この形にした決定（重要）

  1. そのまま再利用: .claude/skills/kiro-*（17 SDLC スキル＝エンジン）・scripts/（swarm/dev-board）・.claude/hooks/format-on-edit.mjs・.claude/settings.json（ガードレール）・rules/reports の README。
  2. 汎用化: CLAUDE.md・steering 一式・ダッシュボードから固有名（製品名・ブランチ・spec 名・技術）を除去。骨格は固有語ゼロ（_examples/ は意図的に実例を保持）。
  3. ペルソナは標準キャストとして残置しつつ、個人名風の苗字は役割ラベルへ匿名化（PO 指示・テンプレのみ）: 統括／運用／Engリーダー／Designリーダー／デザイン実装／デザインRev／実装BE／実装FE／EngRev／QA（絵文字は据え置き）。
  4. 事故記号（A2/K1 等）は「実プロジェクトの例」と注記し、教訓（なぜ）だけ受け取る形に（orchestration.md 冒頭の「テンプレ注記」）。
  5. ダッシュボードは”構造を再利用・中身は例”。冒頭に「📋 これはテンプレート」バナー。数値・タスク・節目・更新履歴はすべて例。
  6. スタック依存の rules は _examples/ へ（アンダースコア＝path-glob 非マッチ＝自動ロードしない参照例）。実スタック向けは実装後に自分で作る。

いま何ができるか（継続の候補）

  • この骨格で新規プロジェクトを開始する（README.md「始め方」の手順：複製 → product/tech/structure 記入 → /kiro-steering → 配役 → /kiro-discovery//kiro-spec-quick → /kiro-impl）。
  • テンプレ自体を磨く: ダッシュボードの例をさらにプレースホルダ寄りにする／review-checklists の骨格に汎用例を足す／_examples/ の rule に「例」ヘッダを付す。
  • GitHub へ公開（テンプレリポジトリ化）— PO 判断。現在ローカル git のみ（初期化済み）。
  • 軽い冗長の手直し: 匿名化で 統括コンダクター 等と役割ラベルが近接する箇所は「役割 ・ 名前スロット」として許容中。実名運用にするなら名前スロットを実名へ。

継続の作法（この手法を使うとき守るもの）

  • 委譲規律 A〜E・証拠で受理（kiro-verify-completion）・独立レビュー（kiro-review）・根本原因デバッグ（kiro-debug）。
  • 状態遷移トリガー（着手→進行中→レビュー中→完了）＋WIP 上限 3、ダッシュボード全体整合（実施=統括／担当=運用）。
  • 堅実性ファースト（ノイズは削る／安全機構・判断根拠・開示・受理ゲートは削らない）。
  • 報告は短文＋図解、末尾に /usage 確認リマインド（推測値は出さない）。
