2026-07-05 パイロット走行報告：progress-digest で SDLC を1周

テンプレート（VERSION 0.1.0）から /var/syslabo/progress-digest を派生し、起動チェックリスト→Discovery/spec→実装→独立レビュー→受理→還流までを実走した。目的は「骨組みが動く」（派生テスト済み）の先、進め方として1周回るかの検証。

結果の要約

  • 1周完走。spec 3フェーズ承認（brief＝代弁ペルソナ3役割当・EARS 16基準・design I/F 6関数・tasks＋トレーサビリティ表16行）→ Maker 実装（feat ブランチ・14テスト全緑）→ 独立レビューAPPROVED（16/16基準・是正要求なし）→ 受理
  • 段階反映②を初実践：代弁ペルソナの brief.md 割当と、要件ID→design節→タスク番号のトレーサビリティ表は、S プリセットの単一 spec でも書く負担が小さく、レビューの突き合わせを速くした（レビュアーが16基準の検算に実使用）
  • 生成規律が効いた：design の I/F シグネチャを委譲プロンプトへ逐語で渡した結果、実装の再解釈ゼロ。さらに Maker が design 内の記述矛盾（出力例 §6.2 と型定義 §7）を発見・開示し、レビュアーが「§7 を正とする解決は要件に違反しない」と独立判定→受理後に design を修正、という開示ループが機能した
  • ドッグフーディングで即価値：完成した CLI をテンプレート本体の実 progress.log（15ストリーム・60行超）に実行し、accept で閉じていない実スレッド2件（design-refine-a・ssg-comparison）を検出。運用上の記録漏れ（受理相当の判断はあったが accept 行を書いていない）を機械が可視化した
  • フィードバックループ初実走：TEMPLATE-FEEDBACK: マーカー4件を派生側の振り返りに記録し、collect-template-feedback.sh が文脈・派生元バージョンつきで抽出できることを確認

テンプレートへの改善提案（収集済み・PO判断待ち）

派生側 2026-07-05-pilot-first-cycle.md から収集した4件。反映する場合は通常の委譲規律（実装→独立レビュー）で行い、VERSION を上げる。

  1. [欠陥] .kiro/settings/templates/specs/ が存在しない：kiro-spec-* スキルが参照するテンプレ群（init.json 等）が本体に無く、kiro-spec-init は「エラー報告して停止」しか道がない。実ファイル同梱か、全スキルへの inline フォールバック明記が要る
  2. [改善] kiro-discovery → full-sdlc.md の相互参照欠落：Stakeholders 節・代弁ペルソナ割当の根拠がスキルから辿れない。SKILL.md へ参照1行
  3. [改善] spec.json の「生成済み・未承認」中間状態が未定義：委譲エージェントによる一括生成→統括/PO の事後承認、という実運用の状態を skills に明記する
  4. [欠陥] init-project.sh の git init が既定ブランチ master を作る：git init -b main へ（テンプレの手順・playbooks は main 前提）

運用面の学び

  • S プリセット（統括がレーンリーダー兼務・実装1＋レビュー1・WIP1）で規律A〜E は無理なく回る。省略したくなる圧力は感じなかった
  • progress.log の記録規約に「受理相当の判断をしたら accept 行を書く」を徹底する価値がある（未完スレッド検出の誤検知はこの記録漏れだけだった）。2回目が観測されたら operations.md へ格上げ
  • 環境固有: この開発環境の node シムは node --test <dir>（ディレクトリ指定）が動かない。glob 展開（node --test test/*.test.mjs）で回避（テンプレの欠陥ではないため還流対象外）

次回への持ち越し

  • 上記フィードバック4件の反映可否（PO判断→採用分は委譲で実装）
  • 派生プロジェクト progress-digest は残置（PO指示）。次 spec 候補＝dispatch/accept 複数回のペア対応追跡（必要が実観測されたら）
