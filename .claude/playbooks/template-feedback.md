# template-feedback.md — テンプレへの還流プレイブック

派生プロジェクト（このテンプレを複製して作られたプロジェクト）で得た学びを、テンプレ本体（この
リポジトリ）へ還流するための、**ゼロ追加インフラ**の仕組み。新しいサービス・DB・外部連携は
使わない。既存の `.claude/reports/`（振り返り）とシェルスクリプトだけで完結する。

## 位置づけ（正本との関係）

`orchestration.md` の振り返り運用に「**2回目の判断は正本（steering／`.claude/rules/`）へ格上げ**」
という原則がある。`template-feedback.md` はこれの**リポジトリ境界を跨ぐ版**——派生プロジェクトの
振り返りで得た知見のうち、「この派生プロジェクト固有」ではなく「**テンプレ自体の欠陥・改善点**」
と判断できるものを、派生先の正本（各プロジェクトの steering／rules）でなく**テンプレ本体**へ格上げ
する経路を用意する。判断基準は同じ——1回限りは派生プロジェクト内に留め、「これはテンプレの構造
自体が悪い」と再認識した時点でマーカーを付ける。

## マーカー規約

派生プロジェクトの振り返り（`.claude/reports/YYYY-MM-DD-*.md`）で、「これはテンプレ自体の改善」
と判断した知見には、行頭に `TEMPLATE-FEEDBACK:` を付けて書く。

```markdown
## 詰まった点・繰り返した判断

- worktree のベース是正ガードで、マーカーファイルの指定を毎回コピペし直していて手間だった。
  TEMPLATE-FEEDBACK: delegation.md の雛形にマーカーファイルの型（既存成果を示すパス1つ＋文字列
  トークン1つ）をプレースホルダごと明示すれば、埋めるだけで済むはず。
```

- マーカー行は**そのまま抽出されて還流フローに乗る**ため、「何が起きたか」でなく「テンプレの何を
  どう直すべきか」まで一文で書く（提案の形にする。単なる感想は還流に値しない）。
- 派生プロジェクト固有の判断（例：この機能特有の設計選択）にはマーカーを**付けない**。テンプレの
  骨格（`orchestration.md`／`operations.md`／`role-catalog.md`／skills／scripts の設計）に関わる
  ものだけに絞る（ノイズ化を避ける＝堅実性ファースト、`operations.md` と同じ判断基準）。

## 還流手順

1. **収集**：テンプレ側（PO・統括）が派生プロジェクトの振り返りを棚卸しするタイミングで実行する。

   ```bash
   scripts/collect-template-feedback.sh <派生プロジェクトのパス>
   ```

   `<派生プロジェクトのパス>/.claude/reports/*.md` から `TEMPLATE-FEEDBACK:` 行を前後の文脈つきで
   抽出し、派生元の `TEMPLATE_VERSION`（どの版から派生したか）とあわせて標準出力へまとめる。

2. **取捨**：抽出結果は提案の集合であり、自動反映はしない。PO が内容を読み、テンプレへ反映するか
   （反映する／保留／却下）を判断する。反映しない場合も理由を残せば、同種の提案が再度上がった際の
   判断材料になる。

3. **反映**：採用したものはテンプレ側の該当ファイル（`.kiro/steering/*`・`.claude/playbooks/*`・
   `scripts/*` 等）を直接編集する。通常の実装委譲と同じ規律（証拠で受理・独立レビュー）に従う。

4. **記録**：反映したら `VERSION` を上げ（[Semantic Versioning](https://semver.org/) に準拠：
   互換性を壊す構造変更＝MAJOR、機能追加＝MINOR、文言修正等の軽微な変更＝PATCH）、
   `CHANGELOG.md` の該当バージョンに「どの派生プロジェクトの提案を」「何を」「なぜ」反映したかを
   記録する（バージョン記録は `.claude/reports/` を経由せず直接 `CHANGELOG.md` へ書く。
   `.claude/reports/README.md` の運用に従う）。

## GitHub 公開後の代替経路

このテンプレが GitHub 上でテンプレートリポジトリとして公開された場合、`TEMPLATE-FEEDBACK:` マーカー
経由の収集に加えて、**テンプレリポジトリへの issue 起票**も還流経路として使える（複数の派生先を持つ
組織で、各派生プロジェクトの `.claude/reports/` へ直接アクセスできない場合の代替）。issue のタイトル
には対象ファイル（例：`role-catalog.md`）を含め、本文にはマーカー行と同じ粒度（「何を」「なぜ」）で
書く。どちらの経路を使うかはプロジェクトの体制に応じて選べばよく、両方を併用してもよい。
