# delegation.md — 委譲プレイブック（コピペで使う雛形）

`orchestration.md` の規律・仕組み（規律A〜E／ベース是正ガード／P1〜P6）を**毎回組み立て直さずに使える形**にしたもの。判断基準（なぜ）は `orchestration.md` が正本。ここは**手順（雛形）**のみ。

## 1. Maker 委譲プロンプト雛形（実装エージェント）

```
あなたは <feature名> の実装担当（<実装BE/実装FE/デザイン実装>）です。
worktree: .claude/worktrees/<feature> / branch: feat/<feature>（起点＝<統合ブランチ>）

## 着手前ガード（必須・省略不可）
1. 以下のマーカーで自分の worktree が最新の起点から作られているか検証する：
   - `git cat-file -e HEAD:<既存成果を示すファイルパス>`
   - `git grep -q "<既存成果を示す文字列トークン>" HEAD`
2. 1つでも欠けたら `git merge <統合ブランチ>` で取り込み、再度 1. を検証する。
   **`git reset --hard` は使わない**（deny 済みの安全ガード。代替は merge で足りる）。
3. 全て OK になるまで実装に着手しない。
4. テストの**合計本数**が現行より少なければ古いベースを疑い、1. からやり直す。

## やること
<タスクの説明・受け入れ条件>

## 禁止事項
- push しない・自分で <統合ブランチ> へ merge しない（統合は統括が行う）
- `.claude/**` の設定・権限ファイルは変更しない
- feat/<feature> 以外のブランチにコミットしない
- 対処療法（例外の握り潰し・フラグ回避・未実装の誤魔化し）はしない。詰まったら止めて共有する（P2）

## 完了報告に必須で含めるもの
- `pwd`（worktree の実際のパス）
- `git log -1 <統合ブランチ>` ＋ 自分の HEAD（ベース是正の証跡）
- 変更ファイル一覧
- テスト/build の実出力（サマリでなく実行結果そのもの）
- コミットしたブランチ名・hash
- 未完の懸念（あれば）。無理に「完了」と書かない
```

## 2. 独立レビュアー委譲プロンプト雛形（Checker）

```
あなたは <feature名> の独立レビュアー（<EngRev/デザインRev>）です。実装したエージェントとは別実体（規律C＝自己レビュー禁止）。

## 手順
1. `kiro-review` スキルの手順に従う。
2. 実装者の完了報告は**信用しない**。まず自分で `git diff` を見て、変更内容を自分の目で確認する。
3. **証拠は自分で再生成する**（規律B）：テストを自分で再実行・build を自分で通す。実装者が貼った出力の転記は受理条件にしない。
4. 受理条件（spec の完了条件・タスクの境界）を機械的に満たしているか確認する。境界外の変更（無関係な混入）がないか確認する。
5. 判定は `APPROVED` / `REJECTED` のいずれか。REJECTED の場合は具体的な指摘と必須の是正内容を書く（人格でなく成果物に向ける＝blameless）。

## 出力に必須で含めるもの
- 実行したテスト/build コマンドと実出力
- 判定（APPROVED/REJECTED）
- 指摘（severity 付き）と必須是正
- 一文まとめ
```

## 3. 受理後の統括手順

1. 独立レビューが `APPROVED` になったことを確認する（`REJECTED` なら (2) へ差し戻し、再委譲か `kiro-debug`）。
2. メイン作業ディレクトリ（`<統合ブランチ>` をチェックアウト中）で `git merge feat/<feature>`。対象ファイルを明示 add（`git add -A` は使わない＝worktree ディレクトリの誤取り込み事故の反省）。
3. `git worktree remove` ＋ merge 済みブランチを `git branch -d` で撤去する。テスト本数の二重カウントが無いことを確認する。
4. ダッシュボード整合：`docs/status.json` を編集し `node scripts/generate-dashboard.mjs` で再生成する（**`docs/status-dashboard.html` を直接手編集しない**）。移動時の整合チェックリスト6項目（①ボード②節目③spec表④KPI⑤見積もり⑥更新履歴）を突き合わせる（`operations.md`）。
5. `.orchestration/progress.log` に1行追記（委譲／受理／統合を開示。規律E）。
6. 破棄した場合も同じ手順で worktree/ブランチを即撤去し、理由を progress.log と完了報告に明示する（黙って消さない）。

## 使い方

- 新規委譲のたびにこの3テンプレをコピペし、`<...>` を埋める。ガード・禁止事項・報告フォーマットを都度手で組み立て直さない。
- テンプレ自体の更新は `orchestration.md`／`operations.md` の変更に追従させる（正本はそちら。ここは写像）。
