# knowledge-graph.md — ナレッジグラフ／オントロジー導入プレイブック

プロジェクトが大規模化した際に、コードベース知識を「フラットな散文」から「Claudeが走査できる構造」へ移行するための判断基準と手順。**このテンプレ自体（数十ファイル規模）には適用しない**——判断基準に照らして適用対象外であり、小規模での導入はノイズ化する（出典1・3の実測が規模比例を示す）。

## 1. 導入判断基準（Thin Slice 原則）

**始め方の原則**：全体を一気にグラフ化しない。「依存関係の質問に毎回リポジトリ全読みが要る」等の**具体的な痛みが出た箇所だけ**を最小範囲でグラフ化し、効果を実測してから広げる（出典7の Thin Slice ＋ このテンプレの「実装が先・ルール化は後」と同じ判断）。

| 導入する                                                                                    | 導入しない                                  |
| ------------------------------------------------------------------------------------------- | ------------------------------------------- |
| 数百ファイル超のコードベース                                                                | 小規模（〜100ファイル程度）＝ノイズ化リスク |
| 依存関係・呼び出し連鎖の横断質問が頻繁（「XはどこからCALLされる？」「変更の影響範囲は？」） | 単発・単純な検索で足りる作業                |
| マルチターンの長期作業・チーム運用                                                          | —                                           |

効果はリポジトリ規模に比例する（出典3のコードレビュータスク実測：125ファイルで26.2倍、2,915で8.1倍、27,732で49.1倍のトークン削減）。

## 2. 手法の選択マトリクス（軽い順に検討する）

| Lv  | 手法                                               | 何が得られるか                                                                                                                                                                                                                                                       | 導入コスト                         | 向く場面                                               |
| --- | -------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------- | ------------------------------------------------------ |
| 1   | **repo map 方式**（Aider型・出典2）                | tree-sitter で AST 解析→グラフランキングで重要シンボルだけを**トークン予算内**（Aiderは既定1,000トークン）の「コードの地図」に自動圧縮                                                                                                                               | 最小（ツール導入のみ）             | まず全体像の把握コストを下げたい                       |
| 2   | **コード構造グラフ**（code-review-graph型・出典3） | tree-sitter→SQLite（nodes/edges）→BFSで**影響範囲（blast radius）**→MCPサーバー経由でクエリ。ノード5種（File/Class/Function/Type/Test）・エッジ7種（CALLS/IMPORTS_FROM/INHERITS等）。ゼロセットアップ（単一 `.db` ファイル）・フックで自動更新・〜50,000ファイルまで | 小（初回ビルド〜10秒/500ファイル） | 依存・影響範囲の質問が頻繁                             |
| 3   | **概念ナレッジグラフ**（MCP Memory Server・出典1） | コード構造でなく**アーキテクチャ知識・ドメイン概念**（「注文サービス depends-on Stripe」等）を型付きリレーションで永続化。マルチホップ推論（推論でなく走査）                                                                                                         | 小（下記手順）                     | アーキテクチャ説明・設計判断の再利用が頻繁             |
| 4   | 本格オントロジー（OWL/SHACL/SKOS等・出典6・7）     | 企業データ統合・複数システム間の意味的統一                                                                                                                                                                                                                           | 大（PoC 1〜3ヶ月〜）               | **このテンプレの範囲外**。必要になったら出典6・7を参照 |

Lv1〜3 は排他でなく併用可（出典1の GraphRAG＝ベクトル検索で初期取得＋グラフ走査で関係分析）。

## 3. Lv3（MCP Memory Server）の導入手順

```bash
claude mcp add --transport stdio memory -- npx -y @modelcontextprotocol/server-memory
```

構築フロー（出典1）：

1. Claude にリポジトリ／設計文書を分析させる
2. `create_entities` — 種類付きノードを作成（例：kind=microservice の "order-service"）
3. `create_relations` — 型付き関係を記録（`calls` / `depends-on` 等。**型付きであることが本質**——タグやフォルダとの違いは関係を「推論」でなく「走査」で辿れること）
4. `add_observations` — 各ノードに役割を短く注記
5. `read_graph` — 検証。保存先は `memory.jsonl`（ローカル・クラウド送信なし）

## 4. 効果測定（導入したら必ずやる）

グラフ有無で**同一の質問**を別セッションで実行し、`/usage` でコスト・トークンを比較する。参考基準（出典1の実測・アーキテクチャ説明タスク）：

| 指標           | グラフなし | グラフあり      |
| -------------- | ---------- | --------------- |
| コスト         | $1.26      | $0.62（約半分） |
| 応答時間       | 2分7秒     | 44秒（約3倍速） |
| キャッシュ読取 | 764.7k     | 118.1k（約1/6） |

効果が出なければ撤去する（「入れたから使う」ではなく、測って判断）。

## 5. コンテキスト汚染への対策（グラフ以前の足場）

出典4は、エージェントの精度低下の主因を**コンテキスト汚染**と特定している。グラフ導入の前提として、この4パターンへの対策が先：

| 汚染パターン | 意味                                   | このテンプレの既存対策                                                                  |
| ------------ | -------------------------------------- | --------------------------------------------------------------------------------------- |
| ①中毒        | 一度生成された誤情報が再利用され続ける | 証拠で受理（規律B）・完了主張を鵜呑みにしない                                           |
| ②劣化        | 古い設計文書・廃止パターンの蘇生       | steering の GC（rules/README.md）・メモリは「書かれた時点の状態」として検証してから使う |
| ③矛盾        | 仕様・コード・コメント間の不整合       | 単一の真実 `status.json`＋派生計算（二重記載の禁止）・整合チェックリスト6項目           |
| ④信号喪失    | ノイズで精度40〜60%低下                | lazy rules（パス連動で必要時のみ読む）・トークン/コスト効率方針（CLAUDE.md）            |

## 6. 既存実践との対応表（このテンプレは核心を独立に実践済み）

外部知見（出典1〜7）とこのテンプレの既存装備の対応。**大規模化した際は、この表を設計図として既存構造をそのままグラフ化できる**：

| オントロジー／エージェント信頼性の概念                                                       | このテンプレでの既存実装                                                            |
| -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| エンティティ＋型付き属性（出典6 Gruber「概念化の明示的仕様」）                               | `status.json`（milestones/specs/board、evidence/lane 種別）                         |
| 関係の明示化＋導出（二重記載の禁止）                                                         | 派生計算（specs→KPI、evidence→badge、milestones→見積もり）                          |
| 制約（Constraints）                                                                          | 整合チェックリスト6項目／M番号は節目専用／実装完了≠受理≠実機検証                    |
| ニューロシンボリック・ガードレール（出典5 技法3＝フレームワークレベルの制約、LLMは回避不能） | `settings.json` deny（`reset --hard` 禁止等）・原則P3「安全レールは個人が変えない」 |
| マルチエージェント検証（出典5 技法4＝実行者・検証者・批評家）                                | Maker≠Checker・独立レビュー（規律C）・証拠で受理（規律B）                           |
| コンテキスト汚染対策（出典4）                                                                | 単一の真実 status.json・steering GC・reports→正本昇格                               |
| 型付きイベントストリーム                                                                     | `progress.log` の dispatch→impl→review→accept                                       |
| LLM生成→別LLM検証（出典7 RIGOR）                                                             | 実装エージェント→独立レビュアーの二段構成そのもの                                   |
