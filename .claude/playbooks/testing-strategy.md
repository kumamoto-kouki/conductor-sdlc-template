# testing-strategy.md — テスト戦略の判断基準（フレームワーク非依存）

このテンプレートから派生するプロジェクトは、スタックを一つに固定しない（Node CLI・Node+SQLite+vanilla JS・将来的には他言語もありうる）。ここに書くのは**特定のテストランナーやフレームワークを前提にしない判断基準**であり、「何のテストを書くか」は各派生プロジェクトの `tech.md`（テスト欄）と `.claude/rules/`（実装が先・ルール化は後）に委ねる。本リポジトリ自身のAstroダッシュボードでの適用例は `.claude/rules/lib-unit-testing.md` を参照（あちらは path-glob 限定のスタック固有ルール、こちらはスタックを問わない判断枠組み）。

## 判断基準

1. **ロジックの種別で優先順位を決める**（言語・フレームワーク非依存）。純粋な計算・変換ロジック（I/O・UI・外部フレームワークに依存しない）を最優先でユニットテスト対象にする。I/O境界（DB・ファイル・ネットワーク）は統合テストか、境界をモックした単体テストで扱う。UI/DOM層は下記4の費用対効果判断に従う。
2. **既存の統合検証で代替可能かを先に確認する**。壊れた入力でビルド・起動自体が失敗する仕組みが既にあり、それが十分な検証入口として機能しているなら、重複するユニットテストは追加しない（本リポジトリの `schema.mjs` はこの例で、`verify-dashboard.mjs` の「壊れた status.json でビルド失敗」チェックが検証入口そのもの）。
3. **テストランナーは派生プロジェクトのスタックに合わせる。統一を強制しない**。Node系なら `node:test`（追加npm依存ゼロ。派生2プロジェクトの実績：ticket-ledger 81本・progress-digest 14本）、他言語ならその言語のエコシステム標準を選ぶ。選定結果は各プロジェクトの `tech.md`「テスト:」欄に記録する（ここは判断基準でなく選定結果の置き場）。
4. **UI/DOMテストは費用対効果で見送ってよい。ただし見送りは常に明示的な代替ゲートとセットにする**。ticket-ledgerのweb-ui specでは「実行時npm依存ゼロ」制約下でDOMテストランナーの新規導入を見送り、代わりにデザインRev＋EngRevの二重ゲート（実ブラウザでの状態網羅・キーボード操作確認）で担保した。この判断自体は妥当だが、「テストが無い」で終わらせず、代替手段を design.md 等に明記する。
5. **負のテストの原則は言語・フレームワークを問わず適用する**。検証チェック（ユニットテストであれ統合テストであれ）を追加・変更したら、検知すべき故障を意図的に起こしてチェックが実際に落ちることを一度証明してから受理する（`.claude/rules/dashboard-verification.md` の原則の一般化）。
6. **実バグの実例を優先度判断の根拠にする**。本テンプレート自身の `derive.mjs` にあったゼロ除算バグ（`totalEstimate=0` → NaN、v0.3.0）は、ユニットテストが無かったため本リポジトリでは検知されず、派生プロジェクトでのビルド後の重い検証サイクルでようやく見つかった。判断基準1（純粋計算ロジックの優先）はこの実例に基づく。
