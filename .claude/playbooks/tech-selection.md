# tech-selection.md — 技術選定の判断基準

機能単位の設計（`design.md` の「技術選定」記入時）と、プロジェクト初期のスタック選定（`tech.md` 記入時）の両方に適用する。

## 1. 最新版でなく最新の安定版を選ぶ

**判断基準**：そのバージョンを前提にする周辺依存が既に追随しているかを確認してから採用する。`dev`／`rc`／`preview` タグは採用しない。

実例（2026-07-09、TypeScript 7 への移行検討）：TS7 は前日に GA したばかりで、Astro の型チェックを担う `@astrojs/check@0.9.9` の `peerDependencies.typescript` は `^5.0.0 || ^6.0.0` までしかカバーしていなかった（npm registry で実測確認）。最新版を採ると本体は動いても周辺エコシステムが追随しておらず統合できない。

確認方法の例：採用候補は `npm view <pkg> dist-tags` で `latest` を確認する。周辺依存は `npm view <dep> peerDependencies` でその依存が対応するバージョン範囲を確認する。

## 2. PO から採用技術の提案があっても、そのまま採用しない

**判断基準**：統括は自分の推奨案を1つ提示し、PO の提案技術と推奨案のメリット・デメリットを並べて PO に判断を仰ぐ。

理由：技術選定の結果は `design.md` に記録され、3フェーズ承認（Requirements → Design → Tasks）の設計フェーズで PO の承認を受ける（`CLAUDE.md` 開発ルール）。承認の対象である以上、統括が PO の提案を無言で採用すると、PO は比較されなかった選択肢を知らないまま承認することになる。加えて、提案は優先度の高い入力であって無条件の正解ではない——`.kiro/steering/role-catalog.md`／`.claude/playbooks/discovery-personas.md` が定める 🧑‍🚀 FDE charter の「現場情報は優先度の高い根拠であって無条件の正解ではない」という認識論と同じ位置づけになる。

なお `orchestration.md` の権限境界が人間の承認を必須とする4カテゴリ（外部公開・破壊的操作・課金・認証）に技術選定は含まれない。PO の判断を仰ぐ根拠は権限境界ではなく、上記の設計フェーズ承認にある。

PO が比較を踏まえて再度同じ技術を指示したら、それが決定である。以後同じ論点を蒸し返さない。

### 諮る対象の線引き

**判断基準**：ここまでの基準（推奨案と並べて PO に判断を仰ぐ）は、その技術選定が PO の業務・運用・費用に影響する場合に適用する。影響しない技術選定は統括が判断し、PO には諮らない。

- 影響する例：アプリの基盤となる構成の選定、PO 側に手作業が発生するかどうかを左右する取り込み方法の選定、継続的な利用料が発生するサービスの選定
- 影響しない例：テストランナーの選定、リンタの選定、内部のモジュール分割

選択の余地がない技術選定（唯一の選択肢しかないが、PO が起動・操作する対象は変わる）は、判断を仰がず報告にとどめる。「報告のみ」と「判断を仰ぐ」の区別は `.claude/playbooks/po-communication.md` §2 に従う。

この線引きは諮る対象の範囲を絞るものであり、諮ると決めた技術選定の扱い（本節冒頭の基準）は変えない。

## 3. Build vs. Adopt との関係

`.claude/skills/kiro-spec-design/rules/design-synthesis.md` §2 Build vs. Adopt は「自作するか既存を採るか」を扱う。本ファイルは、Adopt と決めた後の「どの既存を・どのバージョンで」採るかを扱う。両者は別の問いであり、内容を重複させない。
