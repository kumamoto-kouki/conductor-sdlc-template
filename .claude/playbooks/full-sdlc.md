# full-sdlc.md — 超上流〜保守運用のフルSDLCマッピング

このプレイブックは**既存の仕組みへのマッピング**であり、新しいスキルは作らない。超上流（要求定義）
から保守運用・引き継ぎまでの各フェーズに対して「どの既存スキル/文書を使うか」「何を成果物にする
か」「どの役割が動くか」を対応付け、**現状で薄い保守運用フェーズだけ**手順を新規に書く。

## フェーズマップ

| フェーズ           | 使う既存スキル／文書                                                               | 成果物                                                                              |
| ------------------ | ---------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| 超上流（要求定義） | `/kiro-discovery`                                                                  | `.kiro/specs/<feature>/brief.md`（単一spec）／`.kiro/steering/roadmap.md`（多spec） |
| 要件定義           | `/kiro-spec-requirements`（EARS 形式）                                             | `.kiro/specs/<feature>/requirements.md`                                             |
| 設計               | `/kiro-spec-design`（`/kiro-validate-design` で任意レビュー）                      | `.kiro/specs/<feature>/design.md`                                                   |
| 実装               | `/kiro-impl`                                                                       | 実装コード・commit（worktree 隔離）                                                 |
| 検証               | `/kiro-validate-impl`（feature 横断整合）＋ `kiro-verify-completion`（証拠ゲート） | 検証レポート・独立レビュー判定（APPROVED/REJECTED）                                 |
| リリース           | 通常の統合手順（`delegation.md` 3節）＋セキュリティ監査（着手前投入）              | 統合ブランチへの merge・push 判断                                                   |
| 保守運用           | 本ファイル「保守運用フェーズ」節                                                   | 定期健全性チェック結果・障害是正記録・恒久対策の CHANGELOG/正本への反映             |
| 引き継ぎ           | handoff ドキュメント＋`.claude/reports/`                                           | 引き継ぎメモ・セッション報告                                                        |

役割配置は `role-catalog.md` のフェーズ別投入計画表を正本とする（本表では重複させない）。

### 超上流（要求定義）の詳細

`/kiro-discovery` が超上流を担う。生成される `brief.md` が「なぜ・誰の何を解決するか」、
`roadmap.md`（多spec時）が全体像を表す。**brief.md に最低限含めるべき超上流項目**（現行の
`brief.md` テンプレートの各セクションに対応づけて記入する）：

| 超上流項目                 | brief.md での対応セクション                                                              |
| -------------------------- | ---------------------------------------------------------------------------------------- |
| 背景（なぜ今これをやるか） | `## Problem`／`## Current State`                                                         |
| ステークホルダー           | `## Problem`（誰が困っているか）に明記する。関係者が複数いる場合は箇条書きで追記してよい |
| 成功基準                   | `## Desired Outcome`（「完了したとき何が真になっているか」を検証可能な形で書く）         |
| スコープ外                 | `## Scope` の `**Out**`／`## Out of Boundary`                                            |

brief.md のセクションに厳密に一致しない場合（例：ステークホルダーが複数で独立した節が要る）は、
`## Problem` の直後に `## Stakeholders` を追加してよい（brief.md はテンプレートであり、超上流の
説明責任を果たすための追記を妨げない）。ステークホルダー欄への記入は次の優先順で決める：
①実在のエンドユーザー・現場担当・ステークホルダーに直接当たれるならそちらを書く、
②単一顧客への深い密着案件で **🧑‍🚀 FDE（フォワードデプロイド）** が投入されているなら FDE が
現場で得た一次情報を書く（ただし FDE の情報も無条件の正解ではなく根拠つきで書く。
`role-catalog.md` の FDE charter を参照）、③どちらも無い場合のみ `role-catalog.md` 候補ロスターの
**代弁ペルソナ（🙋 エンドユーザー代弁／🏭 現場代弁／🤝 ステークホルダー代弁）を検証すべき仮説として
書く**（意見でなく仮説として書く運用は `role-catalog.md` を参照）。

### 要件定義〜検証の詳細

- **要件定義**＝`/kiro-spec-requirements`。EARS 形式（Ubiquitous/Event-driven/State-driven/
  Unwanted behavior/Optional）で受け入れ可能な要件に落とす。
- **設計**＝`/kiro-spec-design`。着手前設計判断が要る規模（`role-catalog.md` の候補ロスター
  「設計（アーキテクト）」）では、着手前に設計エージェントを常設する。
- **実装**＝`/kiro-impl`。委譲規律 A〜E・ベース是正ガードは `orchestration.md`／
  `delegation.md` が正本。
- **検証**＝`/kiro-validate-impl`（feature 全体の cross-task 整合・全テスト・spec カバレッジ）
  ＋ `kiro-verify-completion`（完了主張の前に新鮮な証拠を要求するゲート）。**両方**を通す
  ——`kiro-validate-impl` は spec 単位の整合、`kiro-verify-completion` は個々の完了主張の
  証拠ゲートで、役割が異なる（前者を通しても後者を省略しない）。
- **リリース前**＝セキュリティ監査（`role-catalog.md` 候補ロスター）を外部 I/O・認証・公開前に
  投入。**push/公開は PO の判断**（`orchestration.md` 権限境界。統括・実装エージェントは push
  しない）。

## フォワードエンジニアリング強化（発動の判断基準）

要求→要件→設計→タスク→実装という順方向の流れ（フォワードエンジニアリング）自体は Kiro の
3フェーズフローが既に担う。ここに書くのは**強化を発動する判断基準**であり、手順・スキル改修では
ない（機構化は実プロジェクトで2回効いてから＝判断基準を正本へ直接書く既存基準と同一。
`.claude/reports/` は恒久記録の経由地にしない）。

- **トレーサビリティ**：EARS 要件ID→design.md の該当節→tasks.md のタスク番号→commit の対応表を
  spec 内（tasks.md 末尾など既存ファイル内）で維持する。**発動目安＝要件の押し漏れ・実装漏れが
  1回でも実観測されたら、次の spec から導入する**（対応表は spec 単位で完結させ、専用ツールを
  先に作らない）。
- **上流成果物の検証強化**：`/kiro-validate-gap`・`/kiro-validate-design` は現状任意。**発動目安＝
  設計起因の手戻りが観測された spec 種別（例：既存コードへの統合を伴う spec）では、以後実質必須
  として扱う**。正式なゲート化（スキル改修・3フェーズ承認フローの変更）は2回効いてから PO 承認で
  行う。
- **設計からの生成規律**：design.md の I/F・データモデル節は、実装委譲プロンプトへ**逐語で**引き
  渡す（Maker に要約・再解釈させない。`delegation.md` §0 の「逐語ブロック」と同じ理屈＝自然文の
  言い換えは拘束力が落ちる）。**発動目安＝設計と実装の乖離（設計に無い I/F の追加・型の独自変更
  等）が観測されたら**。

## 保守運用フェーズ（現状の最大の不足）

超上流〜検証・リリースは既存スキルで足りるが、**リリース後の定常運用**の手順が薄かったため、
ここに新規で書く。3本柱＝定期健全性チェック／障害対応／引き継ぎ。

### 1. 定期健全性チェック

節目（マイルストーン境界・スプリント境界など）ごとに、運用が主導して以下を回す。**推奨サイクル
＝節目ごと**（固定の日次/週次カレンダーでなく、`operations.md` のチケット状態遷移トリガーと
同じ「起きたイベントに紐づける」思想を踏襲。定常運用でも「気分でなく状態遷移トリガー」の判断
基準は変わらない）：

- **`status.json` 整合**：`operations.md` の移動時整合チェックリスト6項目（①ボード②節目③spec
  表④KPI⑤見積もり⑥更新履歴）を、チケット移動が無い節目でも定期的に流す（ドリフトの早期検出）。
- **依存更新の棚卸し（四半期ごと）**：`npm outdated` で `package.json` の依存（Astro／
  Mermaid／Tailwind／zod 等）が古くなっていないか確認する。メジャーバージョンの更改が
  あれば、`scripts/verify-dashboard.mjs`（`npm run verify`）をゲートに追随作業を行う
  （決定性・実描画・失敗ビルド残留等の受理基準を通してから更新を確定させる。破壊的変更を
  伴う更新は spec 化して `/kiro-spec-quick` で扱う。定常運用の直接パッチは軽微修正に限る＝
  委譲規律 A の「軽微は例外」と同じ線引き）。
- **`.claude/rules/` の GC**：`.claude/rules/README.md` の手入れ規約どおり、対応するコード/
  パターンが消えたルールを削除する。
- **steering の陳腐化点検**：`.kiro/steering/*.md` が実態と乖離していないか（例：配役表に載って
  いない役が実際に動いている、規模プリセットが実態と合わなくなった等）を確認し、乖離があれば
  正本を更新する。
- **検証ハーネス／pre-commitフックは整合チェックリストの機械化**：`scripts/verify-dashboard.mjs`
  （`.claude/rules/dashboard-verification.md` の検証基準を1コマンドで実行）と
  `.githooks/pre-commit`（ビルド入力変更時の再ビルド漏れ防止）は、上記「`status.json` 整合」
  および `operations.md` の整合規約を毎回手作業で確認する代わりに機械で担保するもの。人手の
  定期チェックを置き換えるのではなく、ドリフトを早期に検知する下地として併用する。

### 2. 障害対応

`operations.md`／`orchestration.md` の「**事故 → 是正（blameless）**」ループを、そのまま障害対応
プロトコルとして使う（新しい障害対応フローを別立てしない＝既存機構の転用）：

1. 障害を検知したら、まず**系（しくみ・道具・段取り）の弱さ**として扱う（人を責めない＝blameless、
   `orchestration.md` 信用を支える運用原則）。
2. 応急処置と恒久対策を分ける。応急処置は復旧を優先し、その場しのぎであることを開示する
   （規律 D「肩代わりは黙ってやらない」と同じ——応急処置を恒久対策と偽らない）。
3. **恒久対策は正本へ直接書く**：再発しうる判断基準は `.kiro/steering/`（横断ルール）または
   `.claude/rules/`（パス連動）へ。1回限りの事象はレポート（セッションメモ）に留めてよく、
   2回目で判断基準として正本へ書く（`orchestration.md` 振り返りの運用と同一基準）。
   障害発生・復旧の事実自体は `CHANGELOG.md`（バージョンに影響する場合）に記録する。
4. 障害対応そのものも `.orchestration/progress.log` に開示する（規律E）。

### 3. 引き継ぎ

- **handoff ドキュメント**：後任（人間・エージェント問わず）が読めば再開できる状態を作る。
  最低限、①現在の spec 状況（`/kiro-spec-status`）②未解決の懸念・既知の問題③直近の振り返り
  （`.claude/reports/` の該当ファイルへのリンク）④配役（プリセットS/M/L と実際に動いている役）
  を含める。
- **reports との関係**：handoff ドキュメント自体を新形式で増やさず、`.claude/reports/
YYYY-MM-DD-handoff-<topic>.md` として既存の reports 規約（`.claude/reports/README.md`）に
  従って書く（ファイル形式を増やさない＝理解負債を増やさない）。
- 引き継ぎ後、後任は `/kiro-spec-status` で現状を復元してから着手する。
