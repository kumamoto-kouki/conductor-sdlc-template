# model-assignment.md — モデル選定の判断基準

> **世代ガード**：あなた（読んでいるモデル）の世代が上の `assumed-models` より新しいなら、**本書の価格・挙動の記述を検証せずに信じるな。**PO へ世代交代を報告し、モデル世代適合点検（`full-sdlc.md` の定常運用・台帳は `.claude/maintenance.json`）を提案せよ。世代交代を確実に知っているのは実行中のモデル自身だけであり、この検知はスクリプトでは代替できない。価格・仕様の更新時は `claude-api` skill の出力を正とする。

`CLAUDE.md`「トークン / コスト効率」節の「委譲の階層」で使う詳細判断基準の正本。統括が `Agent` ツールでサブエージェントへ委譲するとき、およびセッション/Workflow で `effort` を設定するときに適用する。役割ごとにモデルを固定する表はここに置かない（同じロールでもタスクの形状でモデルが変わるため。`role-catalog.md` にモデル列を追加しない）。

## 1. コストパフォーマンスの判断基準

**判断基準**：階層を1段上げるとコストは倍以上になる。上げた分に見合う判断の質を要求するタスクかを先に問う。

| モデル           | `model` 値 | 入力 $/MTok       | 出力 $/MTok         | `effort`                   |
| ---------------- | ---------- | ----------------- | ------------------- | -------------------------- |
| Claude Haiku 4.5 | `haiku`    | $1                | $5                  | 非対応（指定するとエラー） |
| Claude Sonnet 5  | `sonnet`   | $3（導入価格 $2） | $15（導入価格 $10） | low〜max                   |
| Claude Opus 5    | `opus`     | $5                | $25                 | low〜max（既定 high）      |
| Claude Fable 5   | `fable`    | $10               | $50                 | low〜max（常時オン）       |

- 機械的な読み取り・特定（grep・ファイル探索・所在確認。判断を伴わない収集）→ `haiku`。判断の要らない作業に Opus を使うのは5倍の無駄になる。
- 実装・レビュー・文書監査 → `sonnet`。
- アーキテクチャ判断・設計レビュー・安全弁に触れる変更 → `opus`。
- `fable` は Opus で品質不足を実際に確認できた場合に限る（Opus の2倍のコスト）。
- **モデル階層より `effort` の方が大きなコストレバーになる場合がある**。Opus の `low`/`medium` は高 `effort` の Sonnet に迫る品質を出すため、「Opus を `medium`」が「Sonnet を `high`」より安く良いことがある。`effort` を指定できる経路では、階層を上げる前に同じモデルで `effort` を上げて測る。

## 2. モデルの特性に合わせた思考の適合

`effort` を指定できる経路（セッション設定・Workflow の `agent()`）と、`Agent` ツール委譲（`effort` パラメータが無く `model` のみ）とでは適合のさせ方が異なる。両者を混同しない。

### `effort` を指定できる経路

既定は `high`。coding／agentic なタスクは `xhigh` に上げる。機械的な作業は `low` に下げる。**Haiku 4.5 は `effort` 非対応のため指定しない**（指定するとエラーになる）。

### `Agent` ツール委譲（`effort` 指定不可）

`effort` を渡せない以上、プロンプトの書き方でモデルの既定の振る舞いに合わせる。**合わせる先は「そのモデルの現に観測される挙動」であって、下の観測メモではない。**

- **判断基準**：委譲プロンプトは、相手モデルの (a) 自発的に検証するか (b) 指示をどこまで字義どおりに読むか (c) 曖昧さを判断で埋めるか、の3点に合わせて調整する。初回の委譲結果でこの3点を観測し、以後の委譲プロンプトに反映する。
- **観測メモ（`as-of` 時点の世代での観測。世代交代したら本節を最優先で棚卸す）**：Opus 系は自分で検証する傾向（検証指示を重ねると過剰検証）。Sonnet 系は字義どおり解釈する傾向（適用範囲を明示しないと省略部分が対象外になる）。Haiku 系は曖昧さを判断で埋めない傾向（探索対象と出力形式の具体指定が要る）。**これは規則ではなく観測であり、新世代へそのまま適用してはならない**——検証が必要なモデルへ「検証指示を書くな」を持ち越すと、委譲プロンプトの質（このハーネスの生命線）が事故に直結する。

## 3. 記録の義務

選定したモデルは規定でなく実績として残す。記入先は**タスクそのもの**——`.kiro/specs/<feature>/tasks.md` の該当タスクに `_Model: <model>_` を注記する（書式は `.kiro/settings/templates/specs/tasks.md`）。`npm run status` がすべての spec の `_Model:_` を集計し、`STATUS.md` に「どのモデルに何タスク割り当てたか」として出す。記録のために別ファイルを持たない（v0.12.0 で手書き正本 `dashboard/status.json` の `modelUsage.entries` を廃止した。実施場所から離れた台帳は誰も更新せず陳腐化する）。

- `_Model:_` は `/kiro-spec-tasks` の時点では**計画**として書かれる。委譲時に別のモデルを選んだら、その場でタスクの `_Model:_` を実際に使ったモデルへ直す（直さなければ集計は計画のままで、実績にならない）。
- 役割にモデルを固定する記録ではなく「その工程のその回でどれを使ったか」の履歴であることを、記入時に混同しない。
- `effort` は `_Model:_` の書式に入らない。指定した場合と、`fable` を選ぶなど説明が要る選定をした場合は、そのタスクの本文か作業記録（`.claude/reports/`）に理由と併せて残す。
