# model-assignment.md — モデル選定の判断基準

`CLAUDE.md`「トークン / コスト効率」節の「委譲の階層」で使う詳細判断基準の正本。統括が `Agent` ツールでサブエージェントへ委譲するとき、およびセッション/Workflow で `effort` を設定するときに適用する。役割ごとにモデルを固定する表はここに置かない（同じロールでもタスクの形状でモデルが変わるため。`role-catalog.md`・`personas.json` にモデル列を追加しない）。

## 1. コストパフォーマンスの判断基準

**判断基準**：階層を1段上げるとコストは倍以上になる。上げた分に見合う判断の質を要求するタスクかを先に問う。

| モデル           | `model` 値 | 入力 $/MTok       | 出力 $/MTok         | `effort`                   |
| ---------------- | ---------- | ----------------- | ------------------- | -------------------------- |
| Claude Haiku 4.5 | `haiku`    | $1                | $5                  | 非対応（指定するとエラー） |
| Claude Sonnet 5  | `sonnet`   | $3（導入価格 $2） | $15（導入価格 $10） | low〜max                   |
| Claude Opus 5    | `opus`     | $5                | $25                 | low〜max（既定 high）      |
| Claude Fable 5   | `fable`    | $10               | $50                 | low〜max（常時オン）       |

- 機械的な読み取り・特定（grep・ファイル探索・所在確認。判断を伴わない収集）→ `haiku`。判断の要らない作業に Opus を使うのは5倍の無駄になる。
- 実装・レビュー・文書監査 → `sonnet`。
- アーキテクチャ判断・設計レビュー・安全弁に触れる変更 → `opus`。
- `fable` は Opus で品質不足を実際に確認できた場合に限る（Opus の2倍のコスト）。
- **モデル階層より `effort` の方が大きなコストレバーになる場合がある**。Opus の `low`/`medium` は高 `effort` の Sonnet に迫る品質を出すため、「Opus を `medium`」が「Sonnet を `high`」より安く良いことがある。`effort` を指定できる経路では、階層を上げる前に同じモデルで `effort` を上げて測る。

## 2. モデルの特性に合わせた思考の適合

`effort` を指定できる経路（セッション設定・Workflow の `agent()`）と、`Agent` ツール委譲（`effort` パラメータが無く `model` のみ）とでは適合のさせ方が異なる。両者を混同しない。

### `effort` を指定できる経路

既定は `high`。coding／agentic なタスクは `xhigh` に上げる。機械的な作業は `low` に下げる。**Haiku 4.5 は `effort` 非対応のため指定しない**（指定するとエラーになる）。

### `Agent` ツール委譲（`effort` 指定不可）

`effort` を渡せない以上、プロンプトの書き方でモデルの既定の振る舞いに合わせる。

- **`opus` へ委譲**：検証を促す指示を書かない（Opus は自分で検証する挙動が既定のため、指示を重ねると過剰検証になる）。簡潔さの指示を足す。スコープ規律の指示を足す。サブエージェント委譲を促す指示は書かない。
- **`sonnet` へ委譲**：プロンプトを字義通りに解釈するため、適用範囲を明示する（例：「最初の1件だけでなく全節に適用」）。省略した範囲は対象外と解釈されうる。
- **`haiku` へ委譲**：判断を求めない。探索対象と出力形式を具体的に指定する（Haiku は曖昧な指示から判断を補って埋める挙動をしない）。

## 3. 記録の義務

選定したモデルは規定でなく実績として残す。工程・ロール・使用モデル・（あれば）`effort`・（あれば）備考を `dashboard/status.json` の `modelUsage.entries` に追記する。役割にモデルを固定する記録ではなく「その工程のその回でどれを使ったか」の履歴であることを、記入時に混同しない。
