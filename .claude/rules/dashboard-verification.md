## ダッシュボードの検証基準

- **正式閲覧はサーバー経由（`npm run preview`＝`scripts/serve-dashboard.sh`）。file:// はコア表示のフォールバック**。PO決定（2026-07-04）で正式な配布・閲覧方式を「Webサーバー経由」に変更し、これまで死守していた file:// 直開き不変条件を格下げした（トレードオフ: file://前提で封じていたESM＝Mermaidの遅延読込・コード分割を解禁し、`dashboard/vendor/mermaid.min.js`（約3.5MB の一括バンドル）を撤去）。file:// で開いたときに要求するのは「CSS適用」「全テキスト情報が読める」ことのみで、**Mermaid図の実描画は要求しない**（module実行がブロックされる環境向けに、生の図コードが崩れて見えないよう案内プレースホルダーへ置き換えるグレースフルフォールバックがあれば足りる）。
- **実描画検証は2段構え**。①**http検証**（正式閲覧相当）: `astro preview` を起動し実際のURL（`http://localhost:<port>/...`）を headless chromium で開き、Mermaid図が実描画されること（svg数・`data-processed="true"`数がいずれも図の総数以上）を確認する。②**file://検証**（フォールバック確認）: file:// で開いてCSSが適用されていること、および未処理の `<pre class="mermaid">` が生テキストのまま露出せずプレースホルダー表示に置き換わっていることを確認する（Mermaid実描画は不要）。
- **見た目に関わる変更は実ブラウザ描画＋スクリーンショットで受理する**。構文チェック（`mermaid.parse()` 等）やDOM存在確認は「表示されるが壊れている」を2回すり抜けた実績がある。headless chromium で実際に開き、スクリーンショットを目視してから合格にする（snap版chromiumは `$HOME` 配下へコピーしてから開く）。
- **「情報量を減らさない」は機械カウントで証明する**。h2/h3/tr/li/バッジ等の要素数とタグ剥がしテキストのdiffを変更前後で比較する。目視やカード枚数の手数えは誤る（実績あり）。カウント手順は再現可能な形で報告に含める。
- **失敗ビルド後の状態も検証対象**。`emptyOutDir:false` 運用のため、ビルド失敗時に内部アーティファクトが `dashboard/` に残留しうる（通常時と失敗時で残留物が異なった実績）。クリーンアップの検証は成功パスだけで済ませない。
- **外部由来のデザイントークンも受理基準（WCAG AA 本文4.5:1・UI3:1）を通す**。「提案どおりの適用」は合格理由にならない（案A適用時に badge-ok 4.095:1 の未達が実発生）。
- **検証チェックの追加・変更は負のテストで実証する**。検知すべき故障を意図的に起こし、チェックが実際に落ちることを一度証明してから受理する。ハーネス自身の盲点が2回実発生した（①要素数減少⚠パスのE2E未検証 ②「data-processed=true かつ svg 存在」だけを見て空描画＝MermaidのID衝突の実故障モードを素通し）。チェックが「通ること」の確認だけでは、チェック自体の欠陥は永遠に見つからない。
