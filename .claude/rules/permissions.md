## 権限リストの組み立て方

- **`defaultMode: "bypassPermissions"` のとき `allow` は完全に無視される**（公式ドキュメント）。効くのは `deny` と `ask` だけである。`allow` の列挙は他モードへ切り替えたときのプリセットとしてのみ意味を持つので、`allow` に足したから安全になった、と考えてはならない。
- **`deny` と `ask` は `bypassPermissions` でも強制される。** だから安全境界はこの2つで作る。
- **振り分けの基準は「取り返しがつくか」**：
  - `deny` ＝ 実行されたら戻せず、このリポジトリの作業に正当な用途が無いもの（`rm -rf`・`shred`・`dd`・`git reset --hard`・`git push --force`・`git filter-branch`）。
  - `ask` ＝ 破壊的だが正当な用途があるもの（`git push`・`git clean`・`find … -delete`・`truncate`・`chmod -R`）。人間が見てから通す。
- **`deny` は前方一致の列挙なので、書き方を変えた同じ操作は素通りする。** `rm -rf` を塞いでも `rm -fr`・`rm -r -f`・`find . -delete`・`git clean -fdx` は別に書かないと止まらない（2026-08-24 の精査で実測）。**列挙で完全に塞げるとは考えないこと。**新しい破壊的コマンドを使ったら、その場でこのリストに足すか、足さない理由を書く。
- **スクリプトの内側までは検査されない。** チェックされるのは Bash ツールに渡したコマンドであって、その先で起動される子プロセスではない。`bash scripts/foo.sh` が内部で何をしても止まらないので、スクリプト自身の安全性は別に担保する。
- **`bypassPermissions` は公式には「隔離環境（コンテナ・VM）でのみ使え」とされている設定である。** このテンプレートが既定にしているのは、委譲と独立レビューを大量に回す設計上、毎回の確認が現実的でないため。**この既定は PO が変更してよい**——同じマシンに git 管理外の大事なものがあるなら `defaultMode` を `auto`（分類器が危険操作だけ止める）へ変えるか、コンテナで動かす。
